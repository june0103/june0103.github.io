# Notion → GitHub Pages 자동 게시

이 스킬은 [Notion 키워드 정리 자동화]의 다음 단계다. 이미 `Claude 정리` 속성이 체크되어 정리 노트가
상단에 작성된 페이지들 중, 사용자가 블로그에 올리고 싶다고 **직접 선택한** 페이지만 게시 대상으로 삼는다.

## 설정값

- **Notion 대상 위치**: https://app.notion.com/p/june0103/120ca3f9e69c8031a7eadf8217827209?v=120ca3f9e69c814194e3000caf438232
  (이 페이지/데이터베이스의 하위 페이지들이 게시 후보다)
- **블로그 저장소**: `june0103/june0103.github.io` (GitHub Pages 사용자 사이트). 저장소 이름이 실제로 다르면
  이 파일의 이 줄을 실제 이름으로 갱신할 것.
- **게시 대상 브랜치**: `main`
- **게시 경로**: `_posts/{YYYY-MM-DD}-{슬러그}.md`
- **소분류 참고 파일**: `_data/categories.yml` (없으면 새로 만든다 — 아래 "카테고리" 절 참고)
- **대분류(1단계, 항상 고정)**: `원티드 AI 네이티브 커리어 캠프`
- **실행 주기**: 매일 20:00 (claude.ai Scheduled Tasks에서 설정. 이 저장소나 Claude Code CLI 세션에는
  스케줄이 저장되지 않으므로, claude.ai 앱/웹의 Scheduled Tasks 화면에서 별도로 등록해야 한다 —
  이 파일 맨 아래 "Scheduled Task 등록 방법" 참고)

## 대상 판별 조건

1. **`Claude 정리` = 체크됨(true)** 인 하위 페이지만 대상으로 한다. 체크 안 된 페이지는 아직 정리 전이므로 건너뛴다.
2. **`GitHub 게시` = 체크됨(true)** 인 페이지만 대상으로 한다. 이 체크는 사용자가 "이 페이지는 블로그에 올려도
   된다"고 직접 선택한 것이므로, 체크 안 된 페이지는 절대 게시하지 않는다.
3. 이미 게시된 페이지인지는 **GitHub 저장소에 해당 파일이 이미 존재하는지**로 판별한다(아래 처리 절차 5번).
   `GitHub 게시` 체크는 게시 후에도 계속 체크된 상태로 남아있으므로, 이 체크 하나만으로는 "이미 게시했는지"를
   구분할 수 없다.
4. 날짜는 **스케줄 실행일이 아니라, 해당 Notion 페이지의 생성일시(created time)** 를 기준으로 한다.

## 처리 절차

1. **대상 목록 조회**: Notion MCP로 위 "Notion 대상 위치" 아래의 하위 페이지 중
   `Claude 정리`=true 이고 `GitHub 게시`=true 인 모든 페이지를 가져온다. 데이터베이스라면 필터 쿼리를,
   일반 페이지 모음이라면 하위 페이지를 순회하며 속성을 확인한다.
2. **날짜 산출**: 각 페이지의 생성일시에서 `YYYY-MM-DD`를 추출한다 (오늘 날짜 아님, 페이지가 실제로 만들어진 날짜).
3. **제목/슬러그/카테고리 결정**: 아래 "제목·슬러그·카테고리 결정 기준" 절을 따른다.
4. **게시용 마크다운 생성**:
   - Front Matter:
     ```yaml
     ---
     title: "글 제목"
     date: {2번에서 산출한 YYYY-MM-DD}
     categories: [원티드 AI 네이티브 커리어 캠프, 소분류]
     ---
     ```
   - 본문은 Notion 정리 노트의 **정리본 부분만** 사용한다. `---` 구분선을 기준으로 그 위(정리본)만 가져오고,
     `## 원본 메모 (정리 전)` 헤딩과 그 아래 내용은 통째로 제외한다.
   - **커밋 전 검증**: 생성한 본문에 `원본 메모`, `정리 전` 같은 문구나 구분선 이후 텍스트가 남아있지 않은지
     다시 확인한다. 남아있으면 제거한 뒤 진행한다.
5. **중복 게시 확인**: 커밋하기 전에 GitHub MCP로 `main` 브랜치의 `_posts/{YYYY-MM-DD}-{슬러그}.md`가
   이미 있는지 확인한다.
   - 이미 있으면 → 이미 게시된 것으로 보고 이 페이지는 건너뛴다(다시 커밋하지 않음).
   - 없으면 → 다음 단계로 진행한다.
6. **커밋**: GitHub MCP로 `_posts/{YYYY-MM-DD}-{슬러그}.md`를 `main` 브랜치에 새 파일로 커밋한다.
   커밋 메시지는 `post: {글 제목}` 형태를 쓴다.
7. **완료 처리**: `GitHub 게시`는 사용자가 직접 체크한 선택 신호이므로 이 값을 바꾸지 않는다(체크 해제하지 않음).
   대신 실행이 끝나면 처리한 페이지별로 게시 완료/건너뜀/실패를 요약해서 보고한다.
   - 커밋이 실패하면 이 페이지는 다음 실행 때 다시 시도된다(5번에서 파일이 없을 것이므로 자연스럽게 재시도됨).
   - 한 페이지 처리 중 오류가 나도 다른 대상 페이지 처리는 계속 진행한다.

## 제목·슬러그·카테고리 결정 기준

### 제목 (title)
- 기본적으로 Notion 하위 페이지의 원래 제목을 그대로 쓴다.
- 페이지 제목이 날짜나 "메모", "정리" 같은 모호한 이름이라 내용을 설명하지 못하면, 정리 노트에서
  비중이 가장 큰 대주제(`##` 헤딩) 이름을 기반으로 제목을 새로 짓는다.
  - 예: 페이지 제목이 "07/25 메모"인데 내용 대부분이 트랜스포머 구조에 관한 것이면 →
    제목을 "트랜스포머 구조 정리"처럼 짓는다.

### 슬러그 (파일명의 영문 부분)
1. 제목에서 핵심 키워드 1~3개를 뽑는다.
2. 이미 널리 쓰이는 기술 용어는 표준 영어 표현을 그대로 쓴다 (트랜스포머 → transformer, 어텐션 → attention,
   파인튜닝 → fine-tuning).
3. 표준 영어 표현이 없는 고유한 한글 표현은 로마자 표기(revised romanization)를 쓴다.
4. 소문자, 하이픈(-)으로 단어 연결, 특수문자·공백 제거. 3~5단어를 넘지 않게 축약한다.
   - 예: "트랜스포머 어텐션 구조 정리" → `transformer-attention-architecture`

### 카테고리 (categories)
- **대분류(1단계)는 항상 `원티드 AI 네이티브 커리어 캠프`로 고정**한다. 모든 게시글에 공통으로 들어간다.
- **소분류(2단계)** 는 정리 노트에서 사용된 대주제(`##` 헤딩) 이름을 그대로 사용한다. 대주제가 여러 개면
  소분류도 배열로 여러 개 넣는다.
  - 예: `categories: [원티드 AI 네이티브 커리어 캠프, NLP]`
- 소분류는 **일관성이 가장 중요**하다. 새 소분류를 만들기 전에, 저장소에 이미 게시된 글들의 기존 소분류를
  먼저 확인하고, 의미가 비슷한 소분류가 있으면 재사용한다.
  - 예: 이미 "NLP"가 쓰인 적 있으면, 비슷한 내용에 "자연어처리"라는 새 소분류를 만들지 않고 "NLP"를 쓴다.
- 기존 소분류 확인은 `_data/categories.yml`을 먼저 본다(GitHub MCP로 조회). 이 파일이 없으면 첫 게시 때
  새로 만들고, 그 시점에 정한 소분류를 첫 항목으로 추가한다. 이후 게시부터는 이 파일을 먼저 확인하고,
  없는 소분류만 새로 추가한다. (매번 `_posts`의 기존 글을 다 열어보는 것보다 빠르다.)
- 소분류 이름 표기 방식(한글 vs 영어)은 처음 정한 방식을 계속 유지한다. 중간에 섞이지 않게 주의한다.

## 하지 말아야 할 것

- **원본 메모(`## 원본 메모 (정리 전)` 이하 내용)는 어떤 경우에도 게시하지 않는다.** 정리본만 게시한다.
- `Claude 정리`가 체크 안 된 페이지는 절대 게시하지 않는다.
- **`GitHub 게시`가 체크 안 된 페이지는 절대 게시하지 않는다** (사용자가 선택하지 않은 자료이므로).
- `GitHub 게시` 속성 값을 임의로 바꾸지 않는다(사용자가 직접 관리하는 선택 신호이기 때문).
- 중복 게시 확인(5번) 없이 바로 커밋하지 않는다 — 같은 파일이 이미 있으면 절대 다시 커밋/덮어쓰지 않는다.
- 게시 날짜를 스케줄 실행일로 넣지 않는다(반드시 페이지 생성일 기준).
- 대분류(`원티드 AI 네이티브 커리어 캠프`)를 빼먹거나 다른 이름으로 바꾸지 않는다.
- 확신 없이 소분류를 새로 만들지 않는다 — 기존 소분류와 비교를 먼저 한다.

## 출력 예시

**대상 Notion 페이지** (생성일: 2026-07-25, `Claude 정리`: 체크됨, `GitHub 게시`: 사용자가 체크함)

**중복 확인**: `_posts/2026-07-25-transformer-attention.md` 파일이 저장소에 없음 → 게시 진행

**생성될 파일**: `_posts/2026-07-25-transformer-attention.md`

```markdown
---
title: "트랜스포머 어텐션 구조 정리"
date: 2026-07-25
categories: [원티드 AI 네이티브 커리어 캠프, NLP]
---

## 트랜스포머 구조

- Self-Attention: 입력 토큰들이 서로 얼마나 관련 있는지 계산하는 메커니즘
- Q, K, V: Query/Key/Value, attention score 계산에 쓰이는 세 벡터
```

**커밋 성공 후**: `GitHub 게시` 속성은 건드리지 않는다. 처리 결과 요약에 "게시 완료"로 기록한다.

## 실행 환경 노트

- 이 스킬은 **claude.ai의 Scheduled Tasks**(매일 20:00 실행)에서 호출되도록 설계되었다. 로컬 Claude Code
  세션의 자체 예약 기능(CronCreate)은 세션이 끝나면(창을 닫거나 컴퓨터를 끄면) 함께 사라지므로 이 용도에
  맞지 않는다.
- 필요한 도구: **Notion MCP**(대상 조회·본문 읽기, 읽기 전용)와 **GitHub MCP**(저장소 파일 조회·생성·커밋).
  두 MCP 모두 실행 환경(claude.ai)에 연결되어 있어야 한다. 정확한 도구 이름은 환경마다 다를 수 있으므로,
  이 문서는 각 단계에서 필요한 동작(조회/필터/조회/파일 존재 확인/파일 생성)을 기준으로 설명한다 —
  실행 시점에 사용 가능한 실제 도구로 매핑해서 수행한다.
- Notion 속성 값을 변경하는 동작은 절대 하지 않는다(이 스킬은 Notion에 대해 읽기 전용으로 동작해야 한다).

### Scheduled Task 등록 방법 (claude.ai 앱/웹)

이 파일 자체는 claude.ai Scheduled Tasks 화면에 자동으로 등록되지 않는다. 아래 절차로 사용자가 직접 등록해야 한다.

1. claude.ai 앱/웹 → Scheduled Tasks(예약된 작업) 메뉴로 이동해 새 작업을 만든다.
2. 반복 주기: 매일 20:00.
3. 프롬프트에는 다음과 같이 이 스킬을 참조하도록 적는다 (저장소 경로가 바뀌면 함께 갱신할 것):
   > `june0103/june0103.github.io` 저장소의 `.claude/skills/notion-to-blog-publish/SKILL.md` 내용을
   > 그대로 따라서 Notion → GitHub Pages 게시 작업을 수행해줘.
4. 이 작업에는 Notion 커넥터와 GitHub 커넥터 접근 권한이 모두 필요하다. 등록 전에 두 커넥터가 연결되어
   있는지 확인한다.
